# Video-service: требования и приёмка

Статус: требования к реализации на основе завершённого архитектурного ревью. Основание — постановка пользователя и корневой `AGENTS.md`. Техническое решение описано в [architecture.md](architecture.md). Приведённые ниже численные ограничения и уточнения бизнес-правил являются предложениями, если явно не следуют из ТЗ.

## 1. Границы и приоритеты

Обязательные технологии: Python + FastAPI, PostgreSQL, frontend, Swagger/OpenAPI по `/docs`. Приложение, БД, объектное хранилище и фоновая обработка запускаются в Docker. Главный результат — воспроизводимый сценарий «регистрация → загрузка → просмотр → лайк → комментарий» и защищённая работа с видео.

- **P0** — критический путь и безопасность; реализуются первыми.
- **P1** — остальные обязательные возможности ТЗ; также необходимы для сдачи. Это порядок реализации, а не разрешение исключить их из результата.
- **P2** — дополнительные возможности вне обязательной сдачи; выполнять только после P0/P1 и согласования объёма.

Масштаб: один сервер, небольшая демонстрационная нагрузка, один worker. Высокая доступность, многорегиональность и промышленный SLA не требуются. Срок нельзя выдерживать за счёт ослабления проверки доступа.

| F01 | P0 | Регистрация по email, `username` и паролю создаёт пользователя с ролью `user` и его единственный канал. Повторный нормализованный email или `username` отклоняется без второй записи. Вход, выход и восстановление пользовательской сессии после обновления страницы работают; после выхода прежняя сессия недействительна. |

| F05 | P0 | Пользователь ставит и снимает один лайк доступному видео. Повторный запрос на установку не создаёт дубликат, повторное снятие безопасно. Состояние и количество сохраняются после обновления страницы. Гость не может менять лайки. |
| F06 | P0 | Доступные видео имеют список комментариев от старых к новым с пагинацией. Авторизованный зритель добавляет непустой текст; автор, время и текст сохраняются. Текст с HTML отображается как текст. Гость не может писать; доступ к комментариям проверяется по доступу к видео. |

Зритель подписывается и отписывается; повторные запросы не создают дубликатов. Самоподписка отклоняется. Список своих подписок доступен пользователю. |
| F08 | P1 | Владелец создаёт, переименовывает и удаляет свои плейлисты, добавляет свои видео, удаляет их и меняет порядок. Чужой пользователь не может изменять плейлист. Публичный плейлист показывает только видео, доступные текущему зрителю; наличие записи не даёт доступа к приватному видео. |
| F09 | P1 | Поиск по подстроке названия без учёта регистра работает для кириллицы и латиницы. Результаты содержат только публичные, готовые, не скрытые видео. Пустой запрос возвращает ленту; спецсимволы `%` и `_` ищутся буквально. Нет результатов — отдельное состояние интерфейса. |

Повторная выдача безопасна, после отзыва следующий медиазапрос запрещён. |

Модератор/администратор видит очередь жалоб, отклоняет жалобу или скрывает видео с обоснованием, может восстановить видео. Скрытый ролик исключён из ленты, поиска, каналов, плейлистов и воспроизведения, включая ранее полученные URL. Действия записываются в журнал модерации. |
| F12 | P1 | Роли `user`, `moderator`, `admin` проверяются сервером. Администратор назначает/снимает роль модератора; пользователь не назначает роли себе, модератор не изменяет роли. Первый администратор создаётся отдельной командой подготовки окружения; публичной регистрации администратора нет. |
| F13 | P0 | Интерфейс напоминает YouTube компоновкой: верхняя панель с поиском, боковая навигация, сетка карточек, страница просмотра с блоком автора и комментариями, страница канала и форма загрузки. При ширине 390 и 1440 px нет горизонтального переполнения; основные действия доступны с клавиатуры, формы имеют подписи. Не копировать чужие логотипы, видео и закрытые ассеты. |

## 3. Видео и хранение

| ID | Требование |
| --- | --- |
| V01 | Принимать локальный файл; загрузка по внешнему URL не поддерживается. Предложенные входные контейнеры: MP4, MOV, WebM, MKV. Расширение и клиентский MIME не считаются подтверждением формата; фактическое содержимое проверяет `ffprobe`. Зашифрованные файлы, плейлисты и файлы без видеопотока отклоняются. |
| V02 | Предложенные лимиты: 500 MiB на файл, длительность от 1 до 600 секунд включительно, размер кадра не больше 3840×2160 с учётом поворота, частота не больше 60 fps. Название: 1–200 символов после обрезки пробелов; описание: до 5000; комментарий: 1–2000; текст жалобы: 1–2000. Лимиты настраиваются и проверяются сервером. |
| V03 | Данные файла передаются и сохраняются порциями с ограниченной памятью. Число реально принятых байтов проверяется даже при отсутствии/ложном `Content-Length`; превышение возвращает `413`. Нулевой файл отклоняется. Одновременно разрешены одна загрузка на пользователя и две на экземпляр API; превышение — `429`. |
| V04 | Оригинал хранится в закрытом объектном хранилище. Worker создаёт один MP4 с H.264, `yuv420p`, AAC при наличии аудио, максимум 1280×720 без увеличения исходника и максимум 30 fps, а также JPEG-превью. Точные параметры кодирования заданы в архитектуре. Оригинал через пользовательский API не раздаётся. |
| V05 | Готовность публикуется только после сохранения и проверки MP4 и превью. Ошибочный файл получает конечное состояние `failed` с понятным кодом ошибки; сообщение не содержит путей, токенов и команд окружения. Скрытие модератором и видимость не сбрасываются обработкой. |
| V06 | Воспроизведение поддерживает `GET`, `HEAD`, одиночный byte range, ответы `200`, `206`, `416` и корректные `Content-Type`, `Content-Length`, `Accept-Ranges`, `Content-Range`. Полный MP4 не загружается в память API. Несколько ranges в одном запросе в первой версии отклоняются с `416`; обычная перемотка браузера работает. |
| V07 | При перезапуске worker задача не теряется; повторная обработка не создаёт второе видео и не позволяет старой попытке опубликовать результат. Временный сбой повторяется ограниченное число раз, неверный медиафайл не запускается бесконечно. |
| V08 | Оригиналы, результаты и метаданные переживают перезапуск контейнеров. Незавершённые загрузки и временные файлы очищаются по сроку хранения. Удаление действительных исходников и видео не является автоматической операцией обслуживания. |

## 4. Доступ и безопасность

| ID | Требование и критерий проверки |
| --- | --- |
| S01 | Проверять права в API для чтения/изменения объектов и каждого запроса к MP4/превью. Подмена `user_id`, `channel_id`, `video_id`, `playlist_id` и ручной вызов API не обходят ограничения. Клиент не определяет владельца и роль. |
| S02 | Приватные видео не попадают в публичную ленту/поиск. Плейлисты не раскрывают недоступные элементы, их названия, превью и количество. Для недоступного видео возвращать одинаковый `404`, включая media/thumbnail endpoints. Личные списки владельца защищены отдельно. |
| S03 | Все медиаобъекты закрыты, включая публичные ролики. S3-порты и административные интерфейсы хранилища не публикуются на хосте; анонимное чтение и запись запрещены. Непредсказуемый ключ, CORS и сокрытие кнопки не заменяют авторизацию. |
| S04 | Не выдавать зрителю S3 credentials и прямые подписанные URL. Отзыв разрешения, перевод в приватное состояние, скрытие и выход из сессии проверяются при следующем запросе, без окна действия старой ссылки. Медиа и чувствительные API-ответы имеют `Cache-Control: private, no-store`; общий кеш отключён. Уже переданные байты отозвать невозможно. |
| S05 | Пароли хранить только как Argon2id-хеши; вход ограничивать по частоте, возвращать одинаковую ошибку для неизвестного пользователя и неверного пароля. Сессионный токен — случайный, хранится в cookie `HttpOnly`, не в `localStorage`; БД хранит его хеш и срок действия. |
| S06 | Для изменяющих запросов проверять точный `Origin`; для сессионных запросов дополнительно CSRF-токен. Использовать параметризованные запросы, валидацию входных полей, текстовый вывод пользовательского содержимого и ограниченный CORS. Роль, пароль и внутренние ключи хранилища не включать в модели общедоступных ресурсов; собственная роль доступна в ответе сессии. |
| S07 | Публичное окружение использует HTTPS и cookie `Secure`. Исключение — явно локальный демонстрационный режим с HTTP на loopback; доступ к удалённому такому стенду возможен через SSH-туннель. Публиковать его напрямую в интернет нельзя. |
| S08 | Не исполнять пользовательские строки в shell, не использовать исходное имя файла как путь. Обработка медиа ограничена по времени, CPU, памяти, протоколам и доступным каталогам. Архивы и ссылки на другие файлы не принимаются как видео. |
| S09 | В репозитории, образах, OpenAPI-примерах и логах нет действующих паролей, cookie, CSRF-токенов и S3-ключей. API не раскрывает пароли/S3-ключи; выдача session cookie и собственного CSRF-токена допустима только предусмотренным контрактом сессии способом. Секреты генерируются для окружения, не выводятся в обычные логи. Не включать исходные AI-журналы в frontend или Docker build context. |

## 5. Развёртывание и эксплуатация

| ID | Требование и приёмка |
| --- | --- |
| D01 | На чистой Ubuntu 24.04 LTS amd64 из распакованного репозитория одна будущая команда `sudo bash scripts/deploy.sh --demo` устанавливает Docker Engine/Compose при отсутствии, создаёт конфигурацию, поднимает компоненты, применяет миграции и заполняет демо-данные. Достаточно `sudo`, доступа в интернет и свободного порта; ручная установка Python/Node/PostgreSQL не требуется. Сам скрипт создаётся на этапе реализации. |
| D02 | Повторный запуск той же команды сохраняет БД, медиа, действующие секреты и пользовательские данные. Скрипт не выполняет очистку volumes и не удаляет конфликтующие пакеты автоматически; при конфликте останавливается с объяснением. Неуспешные миграции/seed/readiness завершают команду ненулевым кодом. |
| D03 | После успешного запуска доступны frontend, `/docs`, `/openapi.json` и `/health/ready` через один origin. Готовность БД/хранилища и свежий heartbeat worker проверены, а не только факт запуска контейнеров. Прямого внешнего доступа к PostgreSQL, S3, worker и API в обход reverse proxy нет. |
| D04 | Именованные volumes сохраняют БД и всё состояние объектного хранилища. В README описаны запуск, остановка без удаления данных, миграции, seed, резервное копирование и восстановление согласованной пары БД + медиа при остановленных writers. |
| D05 | Демо-набор содержит минимум пять пользователей, все три роли, два наполненных канала, шесть коротких видео с превью (включая приватное и скрытое), плейлист, подписки, лайки, комментарии и жалобы. Видео синтетические/разрешённые, не требуют скачивания с YouTube. Повторный seed не дублирует записи и не сбрасывает существующие пароли/пользовательские изменения. |
| D06 | README содержит точные команды проверок, сценарий сдачи, ограничения и способ получения сгенерированных демо-учётных данных из локального защищённого файла. Архитектура и требования соответствуют реализации; версии зависимостей и образы закреплены при реализации. |
| D07 | Для сдачи подготавливается ZIP с полным Git-репозиторием, включая каталог `.git` с осмысленной историей коммитов, оригинальные AI-журналы и фактически использованную агентную обвязку. Рабочие секреты и временные артефакты в ZIP не включаются; состав архива проверяется перед передачей. Коммиты/push выполняются только после согласования. Оригиналы не редактируются; публикация проверяется отдельно, чувствительные оригиналы передаются через согласованный закрытый канал, публичные отредактированные копии помечаются как производные. Не создавать фиктивные журналы или обвязку. |

## 6. Нефункциональные требования

- **N01 — реализуемость:** одно backend-приложение, один хост; обработка отдельным процессом из того же кода. Не вводить отдельный брокер, поисковый кластер, CDN или Kubernetes без доказанной необходимости.
- **N02 — целевое окружение:** предложенный стенд — 4 vCPU, 8 GiB RAM, минимум 30 GiB свободного диска. Все ресурсы, лимиты и результаты измерений фиксируются в README. Это база проверки, а не обещание работы на любом сервере.
- **N03 — дополнительные ориентиры производительности (не обязательные критерии сдачи):** на этом стенде с 1000 карточками и пятью одновременными клиентами p95 ленты/поиска/метаданных ≤ 1 секунды без учёта загрузки медиа; измерять после прогрева минимум на 100 запросах. Для локального просмотра начало готового MP4 ≤ 3 секунд; обработка тестового минутного 720p H.264-ролика ≤ 180 секунд при свободной очереди. Это дополнительные числовые ориентиры, а не обязательные критерии сдачи. Их недостижение само по себе не означает провал приёмки; до измерений не считать их достигнутыми.
- **N04 — ограниченная нагрузка:** один FFmpeg одновременно, ограниченные загрузки и буферы; исчерпание выделенных ресурсов/диска возвращает управляемую ошибку. Ошибки worker не завершают API и не публикуют частичные результаты.
- **N05 — наблюдаемость:** структурированные логи с `request_id`, `video_id`, `job_id`, кодом ошибки; `/health/live`, `/health/ready`, время последнего heartbeat worker, статусы и число попыток задач. Мониторинговый кластер не требуется.
- **N06 — воспроизводимость:** миграции Alembic на пустой PostgreSQL, закреплённые зависимости, предсказуемый seed, тесты на том же типе БД и S3-хранилища, что в Compose.

| T07 | Интеграция + worker | Принудительное завершение worker, повторный захват задачи, устаревший lease, краткий отказ S3/БД, исчерпание попыток; единственный опубликованный результат. | V05, V07, V08, N04 |
| T08 | Compose + чистая VM | Одна команда без предустановленного Docker, `/docs`, readiness, seed дважды, restart без потери данных, проверка закрытых портов и запрета анонимного S3-доступа. | D01–D06, S03, N06 |
| T09 | UI + измерения | Проверка двух размеров экрана, ошибок/пустых состояний, клавиатуры; необязательные измерения N03 с сохранением условий и результатов. | F13, N02, N03 |

Проверки запускаются по мере реализации; фактические результаты фиксируются в отчётах по задачам. Инструменты — pytest, Ruff, TypeScript/ESLint, frontend build и Playwright; конкретные команды появятся вместе с конфигурацией.

## 8. Допущения и открытые вопросы

Все A-пункты ниже требуют учёта при ревью; они не являются дополнительными исходными требованиями пользователя.

| ID | Предложенное уточнение |
| --- | --- |
| A01 | Срок задания — 10 дней с момента получения. Семь дней — оставшееся время на момент обсуждения, а не срок по ТЗ. Дата получения неизвестна, поэтому календарный дедлайн не назначен. Это уточнение пользователя имеет приоритет над прежней формулировкой в `AGENTS.md`; сам файл инструкций по его просьбе не изменяется. |
| A02 | Владелец имеет неявный доступ к своему приватному видео; остальные — только по явному разрешению. Роли модератора/администратора не обходят приватность. Модерация приватного ролика возможна по жалобе без просмотра содержимого либо после добровольной выдачи разрешения владельцем. Подтвердить такую трактовку полномочий. |
| A03 | Есть только `public` и `private`; `unlisted` не требуется. Приватные ролики доступны по ссылке от владельца, не участвуют в общем поиске. Владелец меняет название, описание и видимость; замена файла опубликованного видео не входит в первую версию. |
| A04 | У пользователя один канал. Плейлисты публичные, содержат собственные видео автора; права на каждый элемент независимы от плейлиста. Подписка сохраняет связь и отображает список каналов, отдельная рекомендательная/подписочная лента не обязательна. |
| A05 | Комментарии плоские, без ответов; лайки без дизлайков. Для жалоб причины: `spam`, `copyright`, `abuse`, `other`; одна жалоба пользователя на видео, повтор возвращает существующую. Скрытие только ручное, автоматического порога нет. |
| A06 | Регистрация без подтверждения email; пароль 12–128 символов. Сессия действует 7 суток без бесконечного продления. OAuth, восстановление пароля и управление аккаунтами сверх назначения модераторов — P2. В production эти ограничения потребуется пересмотреть. |
| A07 | Все численные лимиты V02, N02, N03 и ограничения параллелизма предложены для ограниченного срока. Прогресс измеряет отправленные браузером байты; получение 100% не означает завершение записи на сервере. После него показываются отдельные этапы сохранения и обработки, а не выдуманный процент FFmpeg. |
| A08 | Один MP4 и превью достаточны: HLS/DASH, несколько качеств, livestream, resumable upload, CDN, DRM и рекомендации — P2. Разрыв загрузки требует повторной отправки файла целиком. |
| A09 | «Чистая Ubuntu одной командой» означает уже доступный архив/checkout проекта, работающий интернет и `sudo`; поддерживаемая ОС — Ubuntu 24.04 LTS amd64. Демонстрация по умолчанию локальная, HTTP на loopback; публичный домен и TLS-сертификат не предоставлены. Публичное размещение требует отдельной HTTPS-конфигурации. |
| A10 | MinIO — предпочтение, а не обязательный стек. Из-за текущего состояния Community Edition выбрано S3-совместимое SeaweedFS в одном контейнере; обоснование и первичные источники приведены в архитектуре. Выбор хранилища принят на архитектурном ревью. |
| A11 | Удаление видео/аккаунта, пользовательские обложки и аватары, бан пользователей, редактирование/удаление комментариев, обработка апелляций — P2. Скрытие видео обязательно и не означает физического удаления данных. |
| A12 | Точное визуальное сходство оценивается по компоновке и ключевым экранам F13; эталонные скриншоты/макеты не предоставлены. Порядок реализации: сначала защищённый вертикальный сценарий P0, затем все P1, после — стабилизация и сдача. |

Важные ограничения: неизменность оригинальных AI-журналов должна сочетаться с запретом публикации секретов; роль модератора не даёт автоматического права на приватное содержимое. Они учтены в A02 и D07. Архитектура принята как рабочая основа реализации. Git-коммиты и публикация требуют отдельного согласования.
