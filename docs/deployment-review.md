## Реализация

`scripts/deploy.sh --demo` запускается через sudo/root из распакованного проекта.
Проверяет Ubuntu 24.04 amd64, root, интернет/DNS, место в каталоге и Docker data
root, свободный порт или принадлежность действующего web этому проекту.
По умолчанию нужно 8192 МиБ свободного места. Используется локальный Docker socket;
shell overrides конфигурации приложения не подменяют `.env`.

При отсутствии Engine/Compose настраивает официальный apt Docker, устанавливает
пакеты с `--no-remove`, не выполняет curl|sh. Конфликтующие пакеты и отличающиеся
существующие Docker apt sources/key останавливают процесс. Все основные этапы
имеют тайм-ауты с kill-after, ошибки дают ненулевой exit с именем этапа. Журнал локальный 0600,
полная разрешённая Compose-конфигурация и credentials в него не выводятся.

`scripts/deployment_config.py` работает на Python в закреплённом контейнере:
на хосте заранее не нужны Python/Node/PostgreSQL/FFmpeg. Генерирует случайные
секреты только при первом запуске. Compose остаётся единственным парсером dotenv;
разрешённый JSON передаётся по pipe, значения не печатаются. Защищает запись от
симлинков, запрещает публикацию внутренних портов и внешний HTTP origin.
При пропавшем `.env` и существующих volumes проекта — отказ, а не новые секреты.
Отличающийся S3-конфиг не перезаписывается. Общая генерация S3-конфига переиспользует
`scripts/prepare_env.py`; совпадающий файл не обнуляется/не перезаписывается.
Файлы имеют 0600. Для закреплённого SeaweedFS конфиг принадлежит UID/GID 1000:
штатный entrypoint сбрасывает root к этому пользователю.

Порядок запуска: сборка → healthy db/storage → migrate → storage-init →
API/worker и heartbeat → web → seed → HTTP smoke. PostgreSQL, S3, API и worker
не имеют host bindings; web остаётся на 127.0.0.1. Named volumes не удаляются.

`app.cli.seed_demo` — одноразовый сервис профиля demo, использующий существующие
Auth/Channel/Video/Playlist/Interaction/Admin/Moderation services. Bootstrap
аккаунтов выполняется доверенным CLI, публичная регистрация admin не добавлялась.
Синтетические клипы генерируются FFmpeg и отправляются реальным HTTP source API;
затем штатный worker создаёт playback/thumbnail. Прямого создания ready нет.
CLI root нужен только для локальных файлов 0600, runtime API/worker не менялись.

## Идемпотентность и прерывание

`.local/demo/credentials.json` создаётся один раз, содержит случайные пароли,
не выводится в stdout. `.local/demo/state.json` — атомарно записываемый журнал
(temporary file → fsync → replace → fsync каталога), также 0600.

Создание ресурса обёрнуто внешней PostgreSQL-транзакцией: commit существующих
сервисов становится savepoint через `join_transaction_mode=create_savepoint`.
ID pending-результата сохраняется до внешнего commit. После прерывания CLI
проверяет существование именно этого ID: если commit состоялся, ресурс повторно
не создаётся; если rollback — операция выполняется заново. Первоначальная роль moderator и её аудит создаются атомарно с аккаунтом,
чтобы повтор не применял назначение к уже созданному пользователю. Социальные данные,
плейлист, grants и модерация составляют одну такую транзакцию с ID созданного
комментария как проверяемым результатом. Advisory lock запрещает параллельный seed
в одной БД; deploy дополнительно использует flock своего каталога.

Завершённые шаги не применяются заново. Пароли, роли, названия, описания,
плейлисты и другие пользовательские изменения не сбрасываются. При исчезновении
завершённых ресурсов/журнала/credentials скрипт не восстанавливает их выдуманными
данными: нужны исходные файлы резервной копии или решение оператора. Окончательно
failed обработка также требует диагностики; не подделывается статус ready.

```sh
printf '%s\n' '{"execute":"qmp_capabilities"}' '{"execute":"query-status"}' '{"execute":"quit"}' | timeout --kill-after=2 10 qemu-system-x86_64 -machine q35,accel=kvm -cpu host -m 128 -S -nodefaults -display none -nic none -qmp stdio
```

Команда создала только остановленную машину с 128 МиБ RAM, не загружала ОС,
не открывала сетевые интерфейсы и не подключала хостовые диски или Docker socket.
QMP вернул `status=prelaunch`, затем событие SHUTDOWN с `reason=host-qmp-quit`.
Следовательно, установка гипервизора, изменение прав `/dev/kvm` и настройка
host bridge/TAP для следующей попытки не требуются.

Предыдущая диагностика из песочницы сообщала об отсутствии `/dev/kvm` и
`/dev/vboxdrv`; вне песочницы это не подтвердилось. Ошибка VirtualBox IPC при
запуске из песочницы также не означает отсутствия VirtualBox VM на хосте.
Текущий установленный блокер — место, а не отсутствие аппаратной виртуализации.

### Почему Ubuntu VM не создавалась

Для первой сборки README требует минимум 8 ГиБ свободно внутри гостя
(рекомендует 15 ГиБ), дополнительно нужно место под гостевую Ubuntu и её образ.
На постоянном разделе хоста доступно всего около 5,1 ГиБ. Разреженный qcow2
с большим виртуальным размером не резервирует реальное место: установка и
сборка могли бы заполнить общий раздел, где уже работают PostgreSQL и S3.
Понижение `--min-free-mb` не решает эту проблему и для чистой установки не подходит.

`/dev/shm` и `/run/qemu` — tmpfs размером до 16 ГиБ, а не дополнительные диски.
Они используют ту же RAM, которая нужна VM и рабочим приложениям; swap нет.
Размещение полного гостевого диска в RAM не использовалось, чтобы не создавать
давление на память рабочего окружения. Несмонтированные разделы, удаление файлов,
Docker prune, удаление VM/volumes, установка системных пакетов и изменение сети
хоста для обхода ограничения не выполнялись. Платные ресурсы не создавались.

### Минимальный безопасный способ продолжить

Предоставить каталог на постоянном диске с **не менее 30 ГиБ реально свободного
места** под отдельный стенд либо самостоятельно освободить столько на текущем
разделе. Это запас для безопасного испытания с ОС, исходным образом, сборкой и
медиа, а не новое требование установщика и не измеренный размер готовой VM.
Можно использовать уже подключённый внешний диск с подходящей Linux-ФС;
изменение разделов или монтирование существующих NTFS автоматически не предлагается.
Альтернатива — предоставить доступ к отдельной уже созданной Ubuntu 24.04 LTS
amd64 VM без Docker, с sudo, интернетом, 2 vCPU, 4 ГиБ RAM и минимум 15 ГиБ
свободно после установки ОС.

На этом компьютере QEMU/KVM уже пригоден для новой VM. После появления места
можно использовать отдельный образ/диск, QEMU user-mode NAT без bridge/TAP,
только loopback-проброс SSH и SSH-туннель к гостевому localhost:8080.
Хостовый Docker socket/volumes, каталоги данных и существующие VM подключать
не требуется. Установка пакетов или изменение сетевой конфигурации хоста
не нужны для выбранного способа. Загрузка Ubuntu, создание гостевого диска и
этот сетевой запуск пока не выполнялись.

Дальнейший порядок: подтвердить исходную ОС и отсутствие Docker, передать
исходники указанного коммита без `.env`/`.local`/AI-журналов, выполнить ровно
`sudo bash scripts/deploy.sh --demo`, снять приватные контрольные снимки
строк БД (кроме heartbeat), идентификаторов/размеров/хешей медиа и файлов
секретов без вывода значений. Сравнить их после той же команды, после
`sudo reboot` **внутри гостя** и после третьего запуска команды. После reboot
сначала проверить восстановление приложения без запуска установщика.
На каждом этапе повторить readiness, проверку портов/S3 и воспроизведение;
исходные результаты установки пакетов сохранить в защищённом журнале гостя.
Этот порядок — оставшаяся работа, не протокол выполненного испытания.

`time limit reached or command returned 124`. После диагностики выполняется
`exit` с исходным кодом. Ожидаемый отказ `run ... || run ...` сохраняет fallback.
Тело `run()`, его перенаправления в защищённый журнал, значения таймаутов и
