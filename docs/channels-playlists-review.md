## Реализация и контракты

Используется существующий канал, создаваемый при регистрации. Название:
1–200 символов после trim; описание: до 5000. Неизвестные поля, null и NUL
отклоняются. Username нормализуется тем же NFKC/casefold, что в авторизации.

Добавлены API (все пути относительны `/api`):

- `GET /channels/{username}`, `PATCH /me/channel`.
- `GET /channels/{username}/videos`, `GET /channels/{username}/playlists`.
- `PUT/DELETE /channels/{username}/subscription`, `GET /me/subscriptions`.
- `POST /playlists`, `GET/PATCH/DELETE /playlists/{id}`.
- `PUT/DELETE /playlists/{id}/items/{video_id}`, `PUT /playlists/{id}/order`.
- `GET /me/playlists/{id}` — защищённые данные редактора своего плейлиста.

Изменения требуют сессию, точный Origin и CSRF. Роль и владелец не принимаются
от клиента. Владелец плейлиста определяется через канал. Только он может
менять метаданные/элементы/порядок и добавлять только свои видео.
Самоподписка запрещена с 422. Повторные subscribe/unsubscribe/add/remove
идемпотентны; неизвестный или чужой объект изменения возвращает 404.
Удаление плейлиста каскадно удаляет только playlist_items, сохраняя видео.

Публичные видео канала используют общую `public_listing`: public/ready/visible.
Плейлист фильтрует видео **до** LIMIT/cursor через SQL-ветку `watch_listing`
существующего модуля политики доступа: ready/visible и public, владелец либо
grant. Эквивалентность `can_watch` проверена тестами, включая скрытые и
обрабатываемые видео; admin/moderator приватность не обходят. Подписки не
создают grants и не влияют на медиадоступ.

Общие списки возвращают `{items,next_cursor}`, limit=20, максимум 100.
У канальных видео keyset по published_at/id, плейлистов и подписок — по
created_at/id (для подписок — дата создания канала). Cursor привязан к
конкретному списку. У публичных элементов плейлиста cursor содержит только
последний доступный video_id и контекст списка, без абсолютной позиции,
общего количества и пропусков. Недоступная/удалённая опора даёт одинаковый
422 с предложением загрузить список заново; её наличие не раскрывается.
Между страницами порядок может измениться, обновление страницы получает
актуальный список; snapshot-пагинация изменяемого плейлиста не вводилась.

## Схема и конкурентность

Миграция `cc64acf89e63` → родитель `694349d098b8` применена на тестовой и
рабочей БД. Добавляет subscriptions, playlists и playlist_items с FK,
составными PK, индексами обратных FK и channel/created_at/id, CHECK position
и `UNIQUE(playlist_id, position) DEFERRABLE INITIALLY DEFERRED`.
Прежние таблицы и данные не изменяет. `alembic check` прошёл на обеих БД.

Все изменения элементов, порядка и удаление сериализуются блокировкой строки
плейлиста. Перестановка проверяет полный набор video_ids без повторов и
выполняется одной транзакцией; неверный набор ничего не меняет. Подписки
сериализуются блокировкой канала, PK и ON CONFLICT исключают дубликаты.

Отдельный owner-only `/me/playlists/{id}` нужен редактору для полного набора
собственных элементов, включая queued/failed/hidden. Публичная выдача не
расширяется этим контрактом. Это тот же принцип разделения Studio и watch,
что у существующих видео; playback/thumbnail по-прежнему проверяют доступ.
Редактор загружает все страницы своего списка до включения перестановки.

## Frontend

Добавлены `/channels/:username`, `/subscriptions`, `/playlists/:id`,
`/studio/playlists`, `/studio/playlists/:id`. Есть создание, редактирование,
удаление с подтверждением, добавление своих видео, удаление и кнопки порядка.
Канал показывает описание, автора, подписчиков, подписку, публичные видео и
плейлисты. Владелец редактирует канал. Из аккаунта, карточек и watch есть
ссылки на канал; из Studio и sidebar — управление плейлистами. Для гостя
доступно чтение и ссылка входа; кнопки изменения скрыты, серверные запреты
проверяются отдельно. Переходы между страницами перечитывают подписку;
после изменения кнопки данные обновляются событием, при фокусе страницы
метаданные также перечитываются. Уведомления и лента рекомендаций не вводились.
