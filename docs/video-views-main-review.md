## Что установлено и границы вывода

До изменений обычный реальный просмотр нового синтетического ролика работал:
авторизованный зритель увеличил итог с 0 до 1, свежий гостевой Chromium context —
с 1 до 2. Общий отказ всех просмотров в пользовательской вкладке воспроизвести
не удалось. Исходные HTTP-запросы этой вкладки недоступны, поэтому конкретный
первый сбой из пользовательского сообщения не установлен.

Подтверждён дефект обработки отказов: `useVideoViews` при любой ошибке выставлял
`stopped=true` до размонтирования эффекта. Контролируемый единичный HTTP 503 на
`POST /views` на основном стенде воспроизвёл следующую цепочку:

1. Настоящий `HTMLMediaElement` запускается и продолжает воспроизведение.
2. Hook отправляет стартовый запрос и получает 503.
3. `catch` останавливает hook; дальнейших запросов старта или progress нет.
4. В `ViewService` нет подтверждения порога; итог API и UI остаётся 0.
5. Новый тест восстановления на старом frontend падает по timeout 18 секунд.

503 в этом опыте введён перехватом Playwright **только для тестовой страницы**;
инфраструктура и пользовательские запросы не отключались. Это доказательство
ошибки восстановления, а не доказательство исторического 503 у пользователя.

Отдельно задержка настоящего `GET /api/auth/session` выявила гонку: cookie
авторизованного пользователя уже есть, CSRF ещё не загружен, hook отправляет
`POST /views` без CSRF и получает настоящий 403 от backend. Origin при этом
корректен. Восстановление авторизации пересоздаёт плеер на watch-странице;
в этом опыте он остановился на нулевой позиции. Влияние этой гонки на исходную
пользовательскую сессию не доказано.

## Исправление

`frontend/src/features/videos/useVideoViews.ts`:

- ожидание окончания загрузки авторизации перед отправкой событий;
- HTTP-ошибки различаются по статусу; timeout/сеть, 408, 429 и 5xx допускают
  максимум три восстановления за жизненный цикл эффекта, с интервалами 1/2/4 с;
- попытки возникают только из новых событий воспроизведения; таймера повторов
  и дополнительного polling нет; запрос ограничен timeout 8 секунд;
- после сбоя отброшены очередь старых событий и неопределённый интервал,
  новый старт устанавливает новую точку отсчёта; серверная дедупликация сохраняется;
- ошибки доступа/валидации (в том числе 400/403/404/409/422) останавливают попытки;
  404 заменённой сессии не вызывает борьбу вкладок за новую сессию;
- диагностическое предупреждение содержит только статус и решение о восстановлении.

Backend, Origin, CSRF, правила приватности и серверный инкремент не изменены.

`tests/e2e/video_views_recovery.cjs` добавляет воспроизведение нового сценария
и безопасный cleanup синтетических видео в `finally` через DELETE владельца.
Он проверяет потерю ответа уже обработанного progress, восстановление, дедупликацию
авторизованного зрителя и гостя, загрузку CSRF, Range/паузу/seek, ограничение
попыток при постоянном отказе, конкурирующие вкладки, терминальные HTTP-ошибки
и короткое видео. HTTP-отказы, вводимые Playwright, явно отделены от настоящих.

## Проверка итогового изменения

Финальный Chromium E2E: **PASS**, JavaScript page errors: 0. Ролик длительностью
16 022 мс: `09f54153-ee05-4e47-871d-a7cb91409912`. Каждый снимок ниже
сопровождался отдельным SELECT из PostgreSQL, а не выводом счётчика только из API.

| Этап | PostgreSQL | GET API | UI | Число receipts |
| --- | ---: | ---: | --- | ---: |
| До воспроизведения | 0 | 0 | 0 просмотров | 0 |
| Новый авторизованный просмотр после 503 и потери ответа progress | 1 | 1 | 1 просмотр | 1 |

При авторизованном зачёте: HTTP 200, `threshold_ms=10000`, `played_ms=10620`,
`completed=true`, `counted=true`, `views_count=1`. У гостя: HTTP 200,
`played_ms=11652`, `completed=true`, `counted=true`, `views_count=2`.
После reload старт возвращает `completed=true`, `played_ms=0`, `counted=false`:
это 24-часовая дедупликация, а не повторный зачёт. Дальнейшие progress не нужны.
Гостевой cookie — HttpOnly, SameSite=Lax, недоступен через `document.cookie`;
его значение не логировалось и не сохранялось.

При постоянном введённом HTTP 500 получены ровно четыре старта (один + три

серверной сессии получен при конкуренции вкладок; старый плеер не перезапускает
сессию автоматически. Пауза сохраняет реальную позицию, перемотка к концу и
повторные Range (HTTP 206) не достигают порога; последующее реальное воспроизведение
