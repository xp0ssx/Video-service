# Комментарии: ветки, текст и лайки

Приведённые ниже `test-db`/`test-storage`, override-файлы и порт 8081 описывают
исторические проверки этапов. Они не задают постоянный второй стенд. Для новых
изолированных прогонов нужен уникальный Compose project name и автоматический
cleanup контейнеров/сетей по [development.md](development.md). Единственный
постоянный стенд — `video-service`, <http://localhost:8080>; его обновление
описано в README. E2E на другом порту не обновляет основной стенд.

Этап расширяет F06 и заменяет допущение A05 о плоских комментариях из
[requirements.md](requirements.md). Исходные требования не переписываются.
Основа — существующие React/FastAPI/PostgreSQL и слои router → service → repository.
Новых зависимостей нет. Удаление видео, просмотры, установщик и T08 в этот этап не входят.

## Требования и семантика

- Корневые комментарии и ответы идут от старых к новым с устойчивым порядком
  `(created_at, id)` и независимой курсорной пагинацией.
- Один отображаемый уровень: `parent_id = NULL` у корня; у ответа `parent_id`
  указывает на корень. При POST с идентификатором ответа сервис сохраняет
  идентификатор его корня. Вложенная цепочка через API не создаётся.
- У каждого комментария сохраняются ID, автор, время и исходный текст. У корня
  `replies_count` — число ответов этой ветки; у ответов оно равно нулю.
  Индивидуального скрытия комментариев нет: все ответы имеют доступность своего видео.
- Непустой текст содержит 1–2000 Unicode code points, включая пробелы и переносы.
  Строка только из пробельных символов и NUL отклоняются. Валидация не обрезает текст.
- Один пользователь может поставить один лайк корню или ответу; разрешён лайк
  собственного комментария, как у существующих лайков видео. Дизлайков нет.
- Гость читает доступные комментарии и раскрывает ветки, но не пишет и не ставит лайки.

## Диагностика текста

Проверена **локальная реализация до изменений**, включая работающий Compose-стенд.
Восемь примеров из постановки прошли textarea → JSON → FastAPI/Pydantic →
PostgreSQL → API → React → DOM без двойного HTML-экранирования. Сервер не вызывал
HTML escape, React выводил `{comment.body}`, CSS уже содержал `white-space: pre-wrap`
и `overflow-wrap: anywhere`. Это подтверждено исходным кодом и браузерным probe;
прямое равенство значения PostgreSQL проверено добавленными регрессиями.

**Заявленная ошибка двойного экранирования на текущей версии не воспроизведена.**
`<b>Текст</b>` должен выглядеть именно как буквальный текст, а `&lt;` и `&amp;` —
оставаться введёнными последовательностями. Это требуемый безопасный вывод,
а не основание декодировать HTML entities. Происхождение иных ранее экранированных
записей без конкретного примера установить нельзя; массового декодирования БД нет.

Найдены и исправлены реальные расхождения:

1. Форма применяла `trim()` перед отправкой, Pydantic — `strip()` перед записью.
   Теперь они служат только проверке непустоты: пробелы, табы и переносы по краям
   сохраняются. Ранее обрезанные символы восстановить невозможно.
2. JS `length` и HTML `maxLength` считали UTF-16 units, в отличие от Python/PostgreSQL.
   Например, 2000 emoji проходили backend, но ограничивались формой. Теперь форма
   проверяет `Array.from(text).length`, сервер и CHECK остаются окончательной проверкой.
3. У контролируемой textarea внутри label её содержимое влияло на вычисляемую
   метку после ошибки длины. Добавлено стабильное `aria-label="Ваш комментарий"`;
   E2E проверяет дальнейшее редактирование после отказа.

HTML-вставки и `dangerouslySetInnerHTML` не используются. Ответы выводятся тем же
текстовым способом. JSON-экранирование кавычек и обратных слешей — транспортное:
после JSON parse пользователь получает исходную строку.

## API

Все пути ниже имеют префикс `/api`. Маршруты доступны в OpenAPI по `/docs`.

| Метод и путь | Поведение |
| --- | --- |
| `GET /videos/{video_id}/comments` | Страница корней. Прежний маршрут, `limit` (1–100, по умолчанию 20), `cursor`, `items`, `next_cursor` сохранены. |
| `POST /videos/{video_id}/comments` | `201`; JSON `{ "body": "Текст", "parent_id": null }`. Без `parent_id` создаёт корень; с ID корня/ответа — ответ в его ветке. |
| `GET /videos/{video_id}/comments/{comment_id}/replies` | Отдельная страница ответов **корня** с теми же параметрами. ID ответа вместо корня даёт `404`. |
| `PUT /videos/{video_id}/comments/{comment_id}/like` | Идемпотентная установка лайка; возвращает `{ "likes_count": 1, "liked_by_me": true }`. |
| `DELETE /videos/{video_id}/comments/{comment_id}/like` | Идемпотентное снятие; тот же формат состояния лайка. |

Старая форма POST `{ "body": "Текст" }` работает. Прежние поля комментария
сохранены, к ним добавлены `parent_id`, `replies_count`, `likes_count`, `liked_by_me`:

```json
{
  "id": "00000000-0000-4000-8000-000000000001",
  "parent_id": null,
  "author": {
    "id": "00000000-0000-4000-8000-000000000002",
    "username": "example_user"
  },
  "created_at": "2026-01-01T00:00:00Z",
  "body": "<b>Буквальный текст</b>\nВторая строка",
  "replies_count": 2,
  "likes_count": 1,
  "liked_by_me": true
}
```

Старые клиенты продолжают читать и создавать корни; для ответов нужен новый маршрут.
Старые курсоры корней остаются в scope `comments:{video_id}`. Scope ответов содержит
также ID корня: курсор другой ветки/видео или списка корней отклоняется с `422`.
Невалидный UUID/текст/лимит также дают `422`; отсутствующий или чужой parent — `404`.

## Данные и миграция

Добавлена линейная миграция `b7d2e8f91a60_comment_threads_and_likes.py` после
`8e21c4a9d510`. Upgrade не удаляет и не пересоздаёт существующие таблицы.

- Nullable UUID `comments.parent_id`: существующие комментарии остаются корнями.
- `UNIQUE (id, video_id)` и составной FK `(parent_id, video_id)` →
  `comments(id, video_id)` запрещают ссылку на другое видео и отсутствующий parent.
  CHECK запрещает ссылку на себя. Нормализация глубины выполняется сервисом.
- Индекс `(video_id, parent_id, created_at, id)` обслуживает корни, страницы ответов
  и подсчёт ответов в пределах видео; прежний индекс сохранён.
- `comment_likes`: PK `(comment_id, user_id)`, FK к комментариям/пользователям,
  `created_at timestamptz`. PK предотвращает дубли и индексирует подсчёт по комментарию.
- FK video → comments, root → replies и comment → comment_likes имеют `ON DELETE CASCADE`,
  чтобы эти связи не оставляли сирот при будущем согласованном удалении.
  Пользовательские FK сохраняют запрет удаления связанных пользователей.
  Это подготовка связей, API удаления видео не добавлен; остальные видео-связи не менялись.
- Downgrade отказывается выполняться при наличии ответов или лайков комментариев,
  чтобы не потерять новые данные. На пустой схеме проверен полный roundtrip миграций.

Счётчики не дублируются в таблицах. После загрузки страницы выполняются два
агрегатных запроса для её ID: лайки/мой лайк и ответы. Число запросов не растёт
с числом комментариев. Проверка гостевого чтения публичного видео: 4 SELECT для
непустой страницы корней, 5 для ответов, как при limit=1, так и при limit=100.
Автор присоединяется одним JOIN; тела ответов не загружаются со списком корней.

## Доступ, транзакции и лайки

Каждая операция сначала проверяет видео через существующую `can_watch`:
`ready`, `visible`, public либо владелец/private grant. Роль moderator/admin
не даёт обхода private. Hidden запрещён и владельцу, и получателю grant.
Затем комментарий ищется по **паре** comment/video, без раскрытия чужого видео.
Для недоступного видео отсутствующий и существующий комментарии дают одинаковый
`404` с сообщением «Видео не найдено». Ответы API имеют `private, no-store`.

Мутации используют существующие session cookie, Writer/CSRF и проверку Origin.
Гость получает `401`, неверный/отсутствующий CSRF или Origin — `403`.

Лайк устанавливается PostgreSQL `INSERT ... ON CONFLICT DO NOTHING`, снимается
`DELETE` по паре ID. Порядок блокировок сохранён: User KEY SHARE, затем Video UPDATE;
права перепроверяются в этой транзакции. Та же блокировка Video используется
изменениями видимости/grants/модерацией. Мутации одного видео сериализуются,
поэтому конкурирующие повторы возвращают согласованное состояние без дублей.
Это существующая простая стратегия для демонстрационной нагрузки; она ограничивает
параллелизм записей одного популярного видео.

## Интерфейс

Новый `CommentThread.tsx` содержит ветку и действия комментария; корневой список,
лайк видео и интеграция с текущей страницей остаются в `VideoInteractions.tsx`.
Круглые аватары, типографика и цвета берутся из существующей дизайн-системы.

Ответы загружаются только при раскрытии; страницы корней и каждой ветки независимы.
Сворачивание сохраняет загруженные ответы, лайки и курсор. Новые ответы объединяются
по ID, включая случай отправки до загрузки старых ответов. Стабильные React keys
сохраняют состояние веток при лайках, отправке и пагинации корней. Обновление страницы
восстанавливает серверные лайки; ветки первоначально свёрнуты.

Кнопки имеют hover/focus, `aria-pressed`, `aria-expanded`/`aria-controls`; гостевые лайки
отключены. Лайк обновляется после успешного API-ответа, повторная отправка блокируется
до завершения. При ошибке состояние сохраняется, сообщение остаётся рядом с действием;
неотправленный ответ остаётся в форме. Есть загрузка, повтор и догрузка ответов.
При unmount запросы отменяются. Отступ ветки ограничен на мобильном, длинные строки
переносятся. Полная визуальная матрица не запускалась.

## Удаление собственных видео

### Контракт и доступ

`DELETE /api/videos/{video_id}` (путь FastAPI `/videos/{video_id}`, доступен в
OpenAPI `/docs`) возвращает **204 No Content** после commit удаления в PostgreSQL.
Это подтверждение немедленного запрета доступа и сохранённого задания физической
очистки; S3 может ещё очищаться. Требуются действующая сессия, точный `Origin` и
`X-CSRF-Token`. Ошибки: 401 без сессии, 403 при неверном Origin/CSRF, одинаковый
404 для неизвестного и чужого видео, включая приватное. Роли admin/moderator и
private grant не дают права удаления: сервер проверяет `Channel.user_id`.

Повторный DELETE владельца получает 204, не создаёт новое задание и не изменяет
расписание уже существующего. Неизвестный ID возвращает 404. Восстановления нет.
Все пользовательские чтения, включая Studio, feed/search/channel/playlist,
комментарии, replies, лайки, grants и GET/HEAD MP4/JPEG, исключают удалённое видео
и возвращают 404 для обращения к нему. PATCH, повторная отправка исходника,
выдача доступа, добавление в плейлист и восстановление модератором также запрещены.
Закрытый SeaweedFS не выдаёт публичных или подписанных ссылок; старые ссылки ведут
в API и заново проверяют доступ. Уже переданные браузеру байты отозвать невозможно;
открытый до удаления медиапоток не равнозначен новому авторизованному запросу.

### Связи и порядок операций

Реальные FK не позволяют просто удалить `videos`: `VideoAsset`, `VideoJob`,
`VideoAccess`, видео-лайки, playlist items, reports и moderation actions ссылаются
на неё; большинство этих FK без CASCADE. У comments есть CASCADE от video,
составной CASCADE для parent/replies; comment likes каскадно удаляются с комментарием.
Поэтому строка видео остаётся постоянной обезличенной tombstone с `deleted_at`.

В одной транзакции под `FOR UPDATE` строки Video:

1. Проверяется владение. Устанавливается `deleted_at`, стираются название,
   описание, длительность/размеры и upload reservation.
2. Удаляются private grants, лайки видео, все комментарии (вместе с ответами и
   comment likes) и элементы **всех** плейлистов. Плейлисты, каналы, подписки и
   пользователи сохраняются; оставшиеся позиции плейлистов могут иметь пропуски.
3. Reports и moderation actions сохраняют ID, связи, акторов, время, причины-
   категории, решения и переходы состояния. Свободный текст жалобы, review note
   и reason действия заменяется сообщением «Содержимое удалено владельцем»,
   поскольку может содержать цитаты приватного содержимого. Это намеренная
   редакция свободного текста аудита при удалении; исходный текст не сохраняется.
   Жалобы на удалённые видео исключаются из очереди, действия видны в защищённом
   журнале без удалённого содержимого. FK `resolved_action_id` сохраняется.
4. Создаётся единственная `video_deletions` с PK `video_id`; commit делает все
   изменения видимыми вместе. Повтор и конкурирующий DELETE сериализуются на Video.

Assets и processing job остаются внутренними до успешной очистки S3. Worker
удаляет их после удаления исходника, MP4, JPEG, результатов старых попыток и
незавершённых multipart uploads **только** внутри `sources/{video_id}/` и
`processed/{video_id}/`. Ключи проверяются по существующему формату UUID/attempt,
произвольный `VideoAsset.object_key` не даёт права удалить объект другого видео.
Дополнительно проверяются ссылки других videos на очищаемый prefix. Повреждённая
область ключа блокирует очистку с `object_scope_invalid`, требующим диагностики.
Bucket и Docker volumes не очищаются.

### Загрузка, worker и сбои

Новых сервисов нет: долговечную очередь обрабатывает существующий worker перед
claim следующего видео, до десяти заданий за итерацию. Сохраняется инвариант одного
worker/main thread. Tombstone закрывает доступ во всех исходных состояниях:
`awaiting_upload`, `uploading`, `queued`, `processing`, `ready`, `failed`.

S3-запись исходника и результатов FFmpeg держит PostgreSQL advisory transaction
lock, вычисленный из ID видео, и проверяет tombstone после получения lock.
Очистка берёт тот же lock через try-lock; при занятом writer откладывается на
5 секунд с `writer_active`. DELETE берёт только Video и не ждёт S3 writer/job:
поэтому commit запрета доступа не зависит от доступности хранилища или FFmpeg.
Принятие исходника под Video lock после удаления отклоняется, поздний источник
попадает под очистку по prefix. Локальный upload scratch удаляется в finally;
после падения процесса действует прежний безопасный TTL 24 часа в отдельном
scratch API. Scratch worker удаляется при завершении попытки, после crash — по TTL.

Heartbeat, claim, recovery, publish и fail worker проверяют tombstone.
Heartbeat удалённого видео теряет lease и останавливает FFmpeg; завершение старой
попытки не публикует assets или ready и не запускает повтор. Сохраняется порядок
блокировок Job → Video; DELETE не берёт Job, чтобы не создавать обратного порядка.
Очистка assets/job выполняется в том же порядке после внешних операций.

`video_deletions.status` имеет `pending`, `retry`, `complete`; сохраняются
`attempts`, `run_after`, `last_error_code`, `cleaned_at`. При временном отказе S3
видео остаётся недоступным, очередь получает retry с задержкой 10, 20, 40… секунд,
максимум час. В отличие от FFmpeg, число попыток очистки не ограничивается тремя:
обязательство удаления не теряется после долгого отказа. Логи содержат UUID,
безопасный код и попытку, без исходного исключения/credentials. Состояние видно
оператору в таблице; отдельный публичный административный endpoint не добавлен.

Падение после commit tombstone, после части S3-delete или до commit результата
очистки безопасно: новый процесс повторяет идемпотентные операции. Завершённые
задания и tombstones сохраняются и проверяются раз в час. Эта сверка необходима,
поскольку потерянное DB-соединение может отпустить advisory lock раньше завершения
уже отправленной S3-записи; поздний объект также будет удалён. Без tombstone или
при недоступной БД физическое удаление не разрешается. Физическая очистка
асинхронна и зависит от восстановления БД/S3 и работы worker; доступ закрыт сразу.

## Просмотры видео

Этот этап добавляет просмотры к существующим сценариям F02/F03/F07–F09;
исходные обязательные требования не изменяются. Это открытая учебная модель,
а не воспроизведение закрытого алгоритма YouTube. Новых зависимостей и сервисов нет.

### Правило засчитывания

- Для длительности **от 10 секунд включительно** требуется 10 000 ms реально
  воспроизведённого медиавремени. Для ролика короче 10 секунд — половина
  длительности из серверных метаданных, округлённая вверх до миллисекунды.
  Например, у демонстрационного двухсекундного ролика порог равен одной секунде.
- HTMLMediaElement сообщает фактическую позицию; начало — событие `playing`,
  а не открытие страницы, `play()` до начала декодирования или GET метаданных/Range.
- Время накапливается между последовательными отчётами. Сервер принимает не более
  `min(прирост позиции, прошедшее серверное время × предыдущая скорость)`.
  Скорости 0,25–2 соответствуют существующему плееру; на скорости 2× десять секунд
  медиавремени требуют минимум пяти секунд серверного времени.
- Пауза и буферизация завершают активный интервал, возобновление начинает новый.
  `seek` сбрасывает базовую позицию без добавления пропущенного времени;
  `resume` также не добавляет интервал. Отрицательный скачок или прирост,
  превышающий серверный бюджет более чем на 350 ms, целиком отбрасывается.
  Допуск компенсирует дискретность браузерных событий; засчитываемое время
  всё равно ограничено серверным бюджетом. Смена скорости учитывает предыдущую
  скорость для закончившегося интервала.
- Между отчётами допускается максимум восемь секунд. Больший разрыв не добавляет
  время и обновляет базовую позицию. При долгом зависании сети или фоновой
  приостановке вкладки возможен консервативный недоучёт; обычное воспроизведение
  продолжится независимо от аналитики.
- Сессия живёт один час. Новый старт заменяет прежний token и обнуляет незавершённое
  накопление этой пары зритель/видео. Reload и несколько вкладок не складывают
  параллельное время; последняя начавшая воспроизведение вкладка продолжает учёт.

### Зритель и дедупликация

Для аккаунта сервер получает ID исключительно из проверенной сессии входа.
В БД хранится SHA-256 ключ с пространством имён `user:`, без клиентского `user_id`.
Один зритель получает максимум один просмотр конкретного видео за **скользящие
24 часа от последнего засчитанного просмотра**, а не за календарные сутки.
Повторы внутри окна не продлевают его. После истечения окна нужен новый старт
и повторное достижение порога.

Гостю при первом успешном старте выдаётся случайный 256-битный `video_viewer` cookie:
HttpOnly, SameSite=Lax, Path=/, Max-Age=30 дней, Secure по общей настройке HTTPS.
В таблицах хранится только SHA-256 с пространством имён `guest:`. Значение cookie
не продлевается каждым отчётом. Общего гостевого аккаунта, IP-адресов, user agent
или fingerprinting нет. Без cookie или с чужим cookie подтвердить сессию нельзя.
Аккаунт и гостевой браузер — разные идентичности; очистка cookie, другой браузер
или переход от гостя к аккаунту могут создать отдельный просмотр.

### API и права

Все пути имеют префикс `/api`; схемы запросов представлены в `/docs`.

| Метод и путь | Контракт |
| --- | --- |
| `POST /videos/{id}/views` | После `playing`: `{ "position_ms": 0, "rate": 1 }`. Создаёт/заменяет серверную сессию, счётчик не увеличивает. |
| `POST /videos/{id}/views/{session_id}` | `{ "position_ms": 2100, "rate": 1, "sequence": 1, "event": "progress" }`. События: `progress`, `pause`, `resume`, `seek`, `rate`. Сервер проверяет интервал и при достижении порога атомарно засчитывает просмотр. |

Оба маршрута возвращают 200 с `session_id`, `threshold_ms`, `played_ms`,
`completed`, `counted`, `views_count`. `played_ms` — вычисленный сервером итог,
не принимаемый входной параметр. `completed=true` означает, что дальнейшие отчёты
для этой сессии не нужны: порог уже подтверждён либо зритель уже учтён в окне.
`counted=true` возвращается только запросом, который действительно увеличил итог;
повторное подтверждение получает `counted=false` и актуальный счётчик. Повторные
или переставленные `sequence` не меняют накопление. Завершённая сессия внутри
своего TTL также отвечает идемпотентно.

Любой POST требует точного Origin приложения; для действующей сессии входа
дополнительно обязателен существующий X-CSRF-Token. Для гостя обязательный Origin
вместе с SameSite cookie защищает от межсайтового запроса. JSON запрещает лишние
поля, в том числе `user_id`, `played_ms`, `views_count`; PATCH метаданных также
не принимает счётчик. Невалидные поля — 422, Origin/CSRF — 403.

И начало, и каждый отчёт проверяют существующую `can_watch` под блокировкой Video:
готовое, visible, неудалённое видео; public для всех, private для владельца или
зрителя с действующим grant. Владелец учитывается по общему правилу. Роль
admin/moderator не обходит доступ. После revoke, hidden или удаления старый отчёт
возвращает 404 без инкремента, даже если сессия ранее завершилась. Удаление во время
просмотра уничтожает обе записи учёта. Просроченный, заменённый, чужой или
неизвестный session_id также даёт 404. При отсутствии серверной длительности — 409.
GET watch, MP4, JPEG и повторные Range ничего не записывают.

### Данные, конкуренция и срок хранения

Линейная миграция `f2c9a41d6e80_video_views.py` следует за `d4a6c2e91f08`.
Upgrade сохраняет старые видео, комментарии, tombstones и задания удаления;
существующим видео назначается ноль без искусственных seed-просмотров.

- `videos.views_count`: BIGINT NOT NULL DEFAULT 0 с CHECK >= 0. Все read models
  читают это поле, без COUNT событий и без запросов на каждую карточку.
- `video_view_sessions`: PK `(video_id, viewer_key)`, уникальный случайный UUID
  `session_id`, позиция, накопленное время, sequence, скорость, active/completed,
  updated_at/expires_at. Есть CHECK диапазонов и индекс expires_at.
- `video_view_receipts`: PK `(video_id, viewer_key)`, последний `counted_at`, индекс
  counted_at. Это ограниченная память дедупликации, а не полный журнал истории.
- Обе таблицы имеют FK videos с ON DELETE CASCADE. При существующем мягком
  удалении сервис явно очищает их в транзакции tombstone; общий итог остаётся
  обезличенным в недоступной tombstone.

Старт, подтверждение, grant/revoke и удаление сериализуются через FOR UPDATE Video.
Проверка окна, запись receipt и изменение общего счётчика происходят в одной
транзакции. Конкурирующие подтверждения одной сессии засчитывают один просмотр;
разные зрители последовательно увеличивают итог без потерянных обновлений.
Состояние хранится в PostgreSQL и переживает перезапуск API. Блокировка одного
популярного видео ограничивает пропускную способность; для учебного стенда это
минимальный подход без очередей и распределённых счётчиков.

Существующий worker раз в час очищает до 500 просроченных строк каждой таблицы.
Использует тот же порядок блокировок Video и SKIP LOCKED; активный учёт не ждёт
сборщика. При большом накоплении backlog очищается последующими проходами;
оператор может дополнительно выполнить `python -m app.cli.cleanup_views` в
окружении API. Независимо от задержки физической очистки сроки проверяются при
каждом запросе. Очистка записей не уменьшает исторический views_count.
Downgrade запрещён при наличии ненулевого общего счётчика, чтобы не потерять историю.

### Интерфейс и пределы защиты

Количество отображается на главной, в поиске, на watch под заголовком,
в рекомендациях, канале, элементах публичного плейлиста, редакторе плейлиста и Studio.
Общий форматтер выбирает русские формы: 1 просмотр, 2 просмотра, 5 просмотров,
1,2 тыс. просмотров, 1,5 млн просмотров.

Учёт запускается только медиасобытиями. Обычно progress отправляется раз в две
секунды, для короткого порога — чаще; после `completed` запросы прекращаются.
Отдельного постоянного polling просмотров нет. Ранее существовавшая проверка
доступности открытого watch раз в пять секунд сохранена для удаления видео;
она читает метаданные и не создаёт просмотров. Успех отчёта сразу обновляет watch,
запоздавший GET не уменьшает уже показанный счётчик. Повторное открытие получает
актуальное значение сервера. Re-render не начинает сессию заново; при смене видео
или идентичности старые запросы отменяются. Сетевая ошибка аналитики не блокирует
плеер; новая попытка возможна при следующем открытии страницы.

Это защита от обычных повторов, reload, параллельных подтверждений, случайных
дубликатов и перемотки стандартным плеером. Сервер ограничивает скорость
накопления своим временем, но клиентские позиции/события остаются недоверенными:
бот, который ждёт реальное время и имитирует протокол, может пройти проверку.
Удаление cookies и множество идентичностей также обходят простую дедупликацию.
Абсолютная защита от ботов и доказательство человеческого внимания не заявляются.
