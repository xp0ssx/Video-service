# Комментарии: ветки, текст и лайки

Этап расширяет F06 и заменяет допущение A05 о плоских комментариях из
[requirements.md](requirements.md). Исходные требования не переписываются.
Основа — существующие React/FastAPI/PostgreSQL и слои router → service → repository.
Новых зависимостей нет. Удаление видео, просмотры, установщик и T08 в этот этап не входят.

## Требования и семантика

- Корневые комментарии и ответы идут от старых к новым с устойчивым порядком
  `(created_at, id)` и независимой курсорной пагинацией.
- Один отображаемый уровень: `parent_id = NULL` у корня; у ответа `parent_id`
  указывает на корень. При POST с идентификатором ответа сервис сохраняет
  идентификатор его корня. Вложенная цепочка через API не создаётся.
- У каждого комментария сохраняются ID, автор, время и исходный текст. У корня
  `replies_count` — число ответов этой ветки; у ответов оно равно нулю.
  Индивидуального скрытия комментариев нет: все ответы имеют доступность своего видео.
- Непустой текст содержит 1–2000 Unicode code points, включая пробелы и переносы.
  Строка только из пробельных символов и NUL отклоняются. Валидация не обрезает текст.
- Один пользователь может поставить один лайк корню или ответу; разрешён лайк
  собственного комментария, как у существующих лайков видео. Дизлайков нет.
- Гость читает доступные комментарии и раскрывает ветки, но не пишет и не ставит лайки.

## Диагностика текста

Проверена **локальная реализация до изменений**, включая работающий Compose-стенд.
Восемь примеров из постановки прошли textarea → JSON → FastAPI/Pydantic →
PostgreSQL → API → React → DOM без двойного HTML-экранирования. Сервер не вызывал
HTML escape, React выводил `{comment.body}`, CSS уже содержал `white-space: pre-wrap`
и `overflow-wrap: anywhere`. Это подтверждено исходным кодом и браузерным probe;
прямое равенство значения PostgreSQL проверено добавленными регрессиями.

**Заявленная ошибка двойного экранирования на текущей версии не воспроизведена.**
`<b>Текст</b>` должен выглядеть именно как буквальный текст, а `&lt;` и `&amp;` —
оставаться введёнными последовательностями. Это требуемый безопасный вывод,
а не основание декодировать HTML entities. Происхождение иных ранее экранированных
записей без конкретного примера установить нельзя; массового декодирования БД нет.

Найдены и исправлены реальные расхождения:

1. Форма применяла `trim()` перед отправкой, Pydantic — `strip()` перед записью.
   Теперь они служат только проверке непустоты: пробелы, табы и переносы по краям
   сохраняются. Ранее обрезанные символы восстановить невозможно.
2. JS `length` и HTML `maxLength` считали UTF-16 units, в отличие от Python/PostgreSQL.
   Например, 2000 emoji проходили backend, но ограничивались формой. Теперь форма
   проверяет `Array.from(text).length`, сервер и CHECK остаются окончательной проверкой.
3. У контролируемой textarea внутри label её содержимое влияло на вычисляемую
   метку после ошибки длины. Добавлено стабильное `aria-label="Ваш комментарий"`;
   E2E проверяет дальнейшее редактирование после отказа.

HTML-вставки и `dangerouslySetInnerHTML` не используются. Ответы выводятся тем же
текстовым способом. JSON-экранирование кавычек и обратных слешей — транспортное:
после JSON parse пользователь получает исходную строку.

## API

Все пути ниже имеют префикс `/api`. Маршруты доступны в OpenAPI по `/docs`.

| Метод и путь | Поведение |
| --- | --- |
| `GET /videos/{video_id}/comments` | Страница корней. Прежний маршрут, `limit` (1–100, по умолчанию 20), `cursor`, `items`, `next_cursor` сохранены. |
| `POST /videos/{video_id}/comments` | `201`; JSON `{ "body": "Текст", "parent_id": null }`. Без `parent_id` создаёт корень; с ID корня/ответа — ответ в его ветке. |
| `GET /videos/{video_id}/comments/{comment_id}/replies` | Отдельная страница ответов **корня** с теми же параметрами. ID ответа вместо корня даёт `404`. |
| `PUT /videos/{video_id}/comments/{comment_id}/like` | Идемпотентная установка лайка; возвращает `{ "likes_count": 1, "liked_by_me": true }`. |
| `DELETE /videos/{video_id}/comments/{comment_id}/like` | Идемпотентное снятие; тот же формат состояния лайка. |

Старая форма POST `{ "body": "Текст" }` работает. Прежние поля комментария
сохранены, к ним добавлены `parent_id`, `replies_count`, `likes_count`, `liked_by_me`:

```json
{
  "id": "00000000-0000-4000-8000-000000000001",
  "parent_id": null,
  "author": {
    "id": "00000000-0000-4000-8000-000000000002",
    "username": "example_user"
  },
  "created_at": "2026-01-01T00:00:00Z",
  "body": "<b>Буквальный текст</b>\nВторая строка",
  "replies_count": 2,
  "likes_count": 1,
  "liked_by_me": true
}
```

Старые клиенты продолжают читать и создавать корни; для ответов нужен новый маршрут.
Старые курсоры корней остаются в scope `comments:{video_id}`. Scope ответов содержит
также ID корня: курсор другой ветки/видео или списка корней отклоняется с `422`.
Невалидный UUID/текст/лимит также дают `422`; отсутствующий или чужой parent — `404`.

## Данные и миграция

Добавлена линейная миграция `b7d2e8f91a60_comment_threads_and_likes.py` после
`8e21c4a9d510`. Upgrade не удаляет и не пересоздаёт существующие таблицы.

- Nullable UUID `comments.parent_id`: существующие комментарии остаются корнями.
- `UNIQUE (id, video_id)` и составной FK `(parent_id, video_id)` →
  `comments(id, video_id)` запрещают ссылку на другое видео и отсутствующий parent.
  CHECK запрещает ссылку на себя. Нормализация глубины выполняется сервисом.
- Индекс `(video_id, parent_id, created_at, id)` обслуживает корни, страницы ответов
  и подсчёт ответов в пределах видео; прежний индекс сохранён.
- `comment_likes`: PK `(comment_id, user_id)`, FK к комментариям/пользователям,
  `created_at timestamptz`. PK предотвращает дубли и индексирует подсчёт по комментарию.
- FK video → comments, root → replies и comment → comment_likes имеют `ON DELETE CASCADE`,
  чтобы эти связи не оставляли сирот при будущем согласованном удалении.
  Пользовательские FK сохраняют запрет удаления связанных пользователей.
  Это подготовка связей, API удаления видео не добавлен; остальные видео-связи не менялись.
- Downgrade отказывается выполняться при наличии ответов или лайков комментариев,
  чтобы не потерять новые данные. На пустой схеме проверен полный roundtrip миграций.

Счётчики не дублируются в таблицах. После загрузки страницы выполняются два
агрегатных запроса для её ID: лайки/мой лайк и ответы. Число запросов не растёт
с числом комментариев. Проверка гостевого чтения публичного видео: 4 SELECT для
непустой страницы корней, 5 для ответов, как при limit=1, так и при limit=100.
Автор присоединяется одним JOIN; тела ответов не загружаются со списком корней.

## Доступ, транзакции и лайки

Каждая операция сначала проверяет видео через существующую `can_watch`:
`ready`, `visible`, public либо владелец/private grant. Роль moderator/admin
не даёт обхода private. Hidden запрещён и владельцу, и получателю grant.
Затем комментарий ищется по **паре** comment/video, без раскрытия чужого видео.
Для недоступного видео отсутствующий и существующий комментарии дают одинаковый
`404` с сообщением «Видео не найдено». Ответы API имеют `private, no-store`.

Мутации используют существующие session cookie, Writer/CSRF и проверку Origin.
Гость получает `401`, неверный/отсутствующий CSRF или Origin — `403`.

Лайк устанавливается PostgreSQL `INSERT ... ON CONFLICT DO NOTHING`, снимается
`DELETE` по паре ID. Порядок блокировок сохранён: User KEY SHARE, затем Video UPDATE;
права перепроверяются в этой транзакции. Та же блокировка Video используется
изменениями видимости/grants/модерацией. Мутации одного видео сериализуются,
поэтому конкурирующие повторы возвращают согласованное состояние без дублей.
Это существующая простая стратегия для демонстрационной нагрузки; она ограничивает
параллелизм записей одного популярного видео.

## Интерфейс

Новый `CommentThread.tsx` содержит ветку и действия комментария; корневой список,
лайк видео и интеграция с текущей страницей остаются в `VideoInteractions.tsx`.
Круглые аватары, типографика и цвета берутся из существующей дизайн-системы.

Ответы загружаются только при раскрытии; страницы корней и каждой ветки независимы.
Сворачивание сохраняет загруженные ответы, лайки и курсор. Новые ответы объединяются
по ID, включая случай отправки до загрузки старых ответов. Стабильные React keys
сохраняют состояние веток при лайках, отправке и пагинации корней. Обновление страницы
восстанавливает серверные лайки; ветки первоначально свёрнуты.

Кнопки имеют hover/focus, `aria-pressed`, `aria-expanded`/`aria-controls`; гостевые лайки
отключены. Лайк обновляется после успешного API-ответа, повторная отправка блокируется
до завершения. При ошибке состояние сохраняется, сообщение остаётся рядом с действием;
неотправленный ответ остаётся в форме. Есть загрузка, повтор и догрузка ответов.
При unmount запросы отменяются. Отступ ветки ограничен на мобильном, длинные строки
переносятся. Полная визуальная матрица не запускалась.
