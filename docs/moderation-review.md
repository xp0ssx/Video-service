# Шестой этап: жалобы, модерация и роли

Дата: 16 ноября 2026 года. Область: F11/F12, интеграция F13, S01/S02/S04/S06,
A02/A05. Архитектура сохранена. Коммит и push не выполнялись.

## Готовые контракты

- `POST /api/videos/{id}/reports` — только авторизованный зритель с актуальной
  can_watch, причины spam/copyright/abuse/other, непустой trim-текст до 2000.
  Возвращает 200 `{id,status}` и при первом запросе, и при повторе. Повтор
  возвращает существующую жалобу; решение не сбрасывает и текст не заменяет.
- `GET /api/moderation/reports?status=&cursor=&limit=` — moderator/admin,
  статусы open/dismissed/actioned/all, keyset created_at/id по возрастанию,
  limit=20, максимум 100. Cursor привязан к фильтру.
- `PATCH /api/moderation/reports/{id}` — `{status: dismissed|actioned, reason}`.
  Отклонение сохраняет reviewer, обоснование и время, не меняет видео.
  Actioned скрывает видео и связывает жалобу с новым действием hide.
- `PUT /api/moderation/videos/{id}/state` — `{state: hidden|visible, reason}`.
  Меняет только moderation_state; visibility, grants, published_at, assets и
  состояние обработки не меняет. Повтор того же состояния — 200 с action_id=null,
  нового аудита нет. Уже скрытое видео нельзя снова скрыть по другой жалобе:
  PATCH actioned даёт 409; такую жалобу можно отклонить с обоснованием.
- Обработанная жалоба при любом повторном PATCH даёт 409. Повторное открытие
  и пересмотр обработанных жалоб в этом этапе не вводились.
- `GET /api/moderation/actions?cursor=&limit=` — moderator/admin, keyset
  created_at/id по убыванию, журнал hide/restore/set_role без API изменения
  и удаления записей. Выдаются ID целей, автора, старое/новое значение,
  обоснование и время, без приватных метаданных видео.
- Существующие `GET /api/admin/users?username=` и
  `PUT /api/admin/users/{id}/role` сохранены: только admin, точный нормализованный
  username; допустимы user/moderator, действующего admin менять нельзя.
  Повтор той же роли теперь не создаёт фиктивного аудита. NUL в поиске admin
  и обосновании отклоняется до обращения к PostgreSQL.

Все изменения требуют Origin и CSRF, неизвестные поля отклоняются. Actor,
reporter и роли определяются сервером. Роль читается из БД при каждом запросе.

## Транзакции, приватность и гонки

Создание жалобы использует существующую блокировку User key-share → Video и
повторную can_watch под блокировкой; конкурентные запросы сериализуются,
UNIQUE дополнительно исключает дубликаты. Модерация берёт shared-блокировку
actor с перепроверкой роли, затем Video → Report. Публикация worker сохраняет
Job → Video; обращения к grants, visibility и взаимодействиям также
сериализуются на Video. Инверсии порядка Video/Report нет.

Hide, новый аудит и actioned выбранной жалобы фиксируются одной транзакцией.
Fault injection после записи аудита подтверждает откат всех трёх изменений.
Отдельный существующий тест проверяет такой же откат назначения роли.
Конкурентные несовместимые решения дают ровно один успех и один 409.
Проверены одновременные жалобы, hide/visibility/grants и hide/публикация worker.
Последняя сохраняет ready и hidden, не перезаписывая решение модератора.

Служебная очередь намеренно возвращает минимальные данные для **всех** видео:
ID видео/владельца/заявителя, причину, пользовательский текст, статус,
reviewer/note/time и resolved_action_id. Название, описание, превью, медиа и
visibility не выдаются даже при наличии доступа. Действия доступны в журнале.
Жалоба не создаёт grant; moderator/admin без grant не получают private media.

После commit hidden одинаковый 404 получают владелец, получатель grant и
остальные роли: metadata, GET/HEAD media/thumbnail, лайки и комментарии.
Feed/search/channel/playlist фильтруют hidden существующей политикой доступа.
Restore возвращает только исходно разрешённый доступ, включая private grants.
Уже начатый до запрета ответ может завершиться; новые запросы после commit
запрещены. Принудительное прерывание стриминга и DRM не реализовывались.

## Интерфейсы и bootstrap

На watch добавлена форма «Пожаловаться», отражающая стабильный ID повторной
жалобы. `/moderation` показывает фильтр, очередь, отклонение/скрытие,
восстановление по ID и аудит; изменения подтверждаются. `/admin` — поиск,
назначение/снятие moderator с обоснованием и подтверждением. Есть loading,
empty/error states и серверные отказы. Навигация зависит от роли; вход в
служебный раздел и возврат фокуса обновляют сессию. Сервер запрещает следующий
запрос после понижения независимо от состояния интерфейса.

CLI `python -m app.cli.create_admin` уже существовала. Её повтор с тем же admin
теперь идемпотентен, пароль/аккаунт не меняются; конфликт не повышает чужую роль.
Пароль запрашивается через getpass, не через аргументы и не пишется в логи.
Реальный E2E admin создан этим CLI; повтор проверен без ввода нового пароля.

## Исправление F13 по независимому ревью

Независимое ревью шестого этапа подтвердило backend, безопасность,
конкурентность и остальные функции модерации. Найден один блокирующий дефект
приёмки F13: `/admin` с допустимым username из 32 букв `w` при viewport 390 px
имел `document.documentElement.scrollWidth = 441` при `window.innerWidth = 390`.
Новый постоянный сценарий `tests/e2e/admin_layout.cjs` воспроизвёл эти размеры
до исправления.

Причина: результат поиска пользователя выводился обычным `article`/`p` без
переноса длинного слова; правила `overflow-wrap` для `.moderation-card` к нему
не применялись. Исправление локальное: карточке добавлен класс
`.admin-user-card` с `overflow-wrap: anywhere`; странице `.moderation-page` и
этой карточке задан `min-width: 0`, позволяющий сжиматься до доступной ширины.
Порядок имени, роли и кнопки сохранён, глобальный `overflow-x: hidden` не добавлен.
Backend, миграции, README и AGENTS.md в этом исправлении не изменялись.

Chromium E2E использует настоящий API и сессию отдельного CLI-admin из
защищённого `MODERATION_ACCOUNTS_FILE` вне Git. Подставных HTTP-ответов нет.
Пользователь `w × 32` находится через API или регистрируется, если отсутствует;
короткий синтетический username регистрируется с уникальным именем. Исходные
роли восстанавливаются в `finally`, включая неуспешный прогон; аккаунты и
существующие данные не удаляются. Прогон добавляет синтетический аккаунт и
записи аудита назначений/снятий ролей.

Результаты постоянной регрессии после исправления:

| Viewport | Ширина документа | Username `w × 32` | Короткий username | Роль и действия |
| --- | --- | --- | --- | --- |
| 390 px | 390 px | Все 32 символа, две строки | Одна строка | Видны, без наложений |
| 1440 px | 1440 px | Все 32 символа, одна строка | Одна строка | Видны, без наложений |

На каждой ширине для обоих имён проверены начальная роль user, назначение
moderator и снятие до user через UI с клавиатуры и успешным PUT API. Проверки
геометрии каждого символа подтверждают полный вывод внутри карточки и main;
имя не пересекает роль, кнопки или поля. Поля и кнопки не пересекаются и
помещаются в main. Короткое имя сохраняет обычное отображение. Ошибок console
и pageerror нет. Снимки обеих ширин просмотрены, артефакты находятся вне Git в
`/tmp/vs6-f13-artifacts/`.

### Оставшиеся неблокирующие замечания независимого ревью

1. CHECK для рассмотренной жалобы допускает `review_note = NULL` при прямом
   SQL INSERT: SQL CHECK пропускает UNKNOWN. Нужна отдельная корректировка
   ограничения, не только валидация API.
2. Downgrade миграции `3f32713066d6` конфликтует с существующим аудитом
   hide/restore. Обратную миграцию необходимо разобрать отдельно с учётом
   сохранности аудита.
3. README содержит устаревшее описание возможностей модерации.

Эти замечания зафиксированы без изменения backend и миграции; по решению
архитектора они будут разобраны отдельно до сдачи.
